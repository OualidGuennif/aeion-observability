# What this repository is, today — 2026-11-01

Scope: what runs, what is measured, what is redundant, and what the owner's four requirements need.
Every "verified" line below was executed on this machine on 2026-11-01; the long form with commands
is in [validation.md](validation.md#local-stack-end-to-end-and-langfuse-v4--2026-11-01).

## 1. One sentence

A research workspace that runs **real coding agents** (Flue 2.3.0 on Pi 1.4.0, in three execution
tiers) behind a **host-native supervisor** that owns the model credential, counts context, forces a
checkpoint at 250k and a handover, verifies the produced artifact in a fresh sandbox, and sends
metadata-only evidence to a **local Langfuse** while two memory services keep what a later agent
needs.

## 2. Four layers, and what each one owns

| Layer | Where | What it owns | Size |
| --- | --- | --- | --- |
| Research and contracts | `knowledge/`, `examples/`, `tests/` | The component spec, the telemetry contract, the synthetic fixtures and their arithmetic | 33 tests |
| Host controller | `demo/app/` (Python, native) | The Go key, the counting relay, the 250k/300k gates, the handover Markdown, the audit, the checks, the cockpit API | ~4,500 lines |

| Local pilot | `demo/compose.yaml` | Langfuse 4.49.0, ClickHouse, Postgres, MinIO, Redis, OTel collector, Deno playground, Hindsight, claude-mem | 10 services, ~8.3 GB of limits |

Repository totals: 320 tracked files, ~11,000 lines of Python, ~1,600 lines of JS/TS, 112 Markdown
documents.

**One stack, not several.** `demo/compose.yaml` is a single Compose project started with one
command; the supervisor, the relay and the Flue harness are host processes, not containers. Adding
Langfuse, claude-mem or Hindsight did not multiply the number of stacks.

## 3. The three pillars the owner named

### claude-mem — carry the checkpoint

- **What it does here:** stores one bounded working checkpoint per run through its explicit save/read
  API (`platformSource: "pi"`), with the artifact digest, the agent number and the check results.
- **Verified:** run `652bbc…` saved and read back checkpoint `#2`; the cockpit shows the id and the
  digest.
- **Limit:** it is working memory, not knowledge. It does not judge, summarize or rank; it returns
  exactly what was written.

### Flue — generate the agents

- **What it does here:** runs Pi with tools, skills and a sandbox adapter. Tier 1 is an in-memory
  `just-bash` shell, tier 2 confines file tools to a folder, tier 3 runs every tool call inside
  NVIDIA OpenShell 0.1.5 through a loopback bridge.
- **Verified:** `qualify_flue.py --local-sandbox` re-ran today on the real Flue CLI with fake
  inference — tier 3 six requests and two fresh conversations over a 250k handover, 12/12 checks;
  tier 2 five requests, 12/12; tier 1 five requests, 8/8. Complete usage, no compaction, no prompt
  text in events.
- **Limit:** tier 3's real sandbox is qualified on Linux CI and **not on this Mac** (section 4).

### Langfuse — capture what happens

- **What it does here:** receives OTLP/HTTP from the OTel collector with the v4 ingestion header.
  The collector keeps a fixed attribute allowlist, so prompts, tool payloads and stacks never reach
  it from the supervisor path.
- **Verified:** today's synthetic triage replay produced 22 observations (`demo.task`,
  `agent.started`, `gen_ai.request` ×5, `gate.closed`, `handover.prepared` ×3, `agent.handover`,
  `artifact.checked`, `session.wiped`, `memory.checkpoint`, `memory.retained`, `quality.scored`),
  and both boolean scores were accepted.
- **Second producer, verified separately:** the `@langfuse/pi-observability-plugin` 0.1.2 ran from
  `.tmp/pi-agent` and produced three `Conversational Turn` spans and three `LLM Call` generations
  in `environment=development`, with tokens, latency, TTFT and the raw prompt attached.
- **Limit:** on this Langfuse 4.49.0 instance (`events_only`), `GET /api/public/traces`,
  `/sessions` and `/scores` are 404. Reads must use `GET /api/public/v2/observations` and
  `/api/public/v2/metrics`. Any script that still calls the v1 resources is dead.

## 4. The third tier and OpenShell, measured

`demo/openshell/setup.py` builds the agent image, starts the gateway and then fails the security
qualification: the probe's `exec` returns an empty stdout. The cause is now measured, not assumed.

- On the host-backed work volume, writes are **performed** — the files appear on the host — while the
  syscall returns `EACCES`. `open(..., "w")`, `: > file` and `echo > file` fail this way; `touch`
  sometimes succeeds; repeated probes disagree with each other.
- The same write succeeds in a plain container on the same bind mount and on a Docker volume-subpath
  mount; `os.access(..., W_OK)` is `True`; `/tmp`, `/sandbox` and a tmpfs mounted inside the sandbox
  all accept writes normally.
- Host bind mounts are refused by admission ("host bind or image mount cannot be attached while
  resource admission is enabled: no trusted label resolver"), so the volume path is the only one the
  gateway admits.

The qualification fails closed, exactly as designed, and tier 3 stays unavailable locally. The
three tiers still pass end to end against a host stand-in, and on Linux CI in a real sandbox.

**Two honest options.**

1. **Run tier 3 where it is qualified** — Linux CI, a Linux host, or a Linux VM. No code change.
2. **Move the workspace off the shared mount** — copy the run workspace into the sandbox with
   `client.exec(stdin=...)` and read it back with `cat`, keeping identical absolute paths so the
   bridge and the checks do not change. The SDK already supports stdin, and tmpfs is writable, so
   this is a bounded change in `demo/app/sandbox.py` plus its call sites — but it replaces a
   Linux-qualified path and needs a new qualification on both platforms.

I did not apply option 2 blind: it touches the security boundary the repository exists to prove.

## 5. The cockpit

`python3 demo/run.py` serves a native page on `127.0.0.1:8088`: ivory, forest green and copper,
serif headings, no dark "future dashboard". It shows the live session lifecycle, the KPI cards, the
model-lab scatter, the two memory rooms, and now a **fleet strip** above the sessions: the six most
recent runs across all tiers, with tier, status, task, model, checks, duration and a link to
Langfuse.

What it is not: a multi-session manager. It runs one active run at a time and keeps the rest as
evidence. That is a deliberate limit, not a missing feature.

## 6. Is the setup over-engineered?

**The supervisor is not over-engineering.** It owns four things Flue does not: the subscription key
(which never reaches the harness), the request counting and admission gate, the 250k checkpoint and
the retirement of the old session, and the deterministic verdict in a fresh sandbox. Removing it
would move the key into the agent process and delete the evidence.

**Three places are heavier than the requirement.**

1. **Telemetry has two producers.** The supervisor builds metadata spans by hand because Flue's own
   OTel adapter exports prompts, tool payloads and stacks by default. A redacting collector in front
   of that adapter would remove the hand-built mapping — at the cost of trusting the redaction.
2. **Memory has two services.** claude-mem carries one checkpoint; Hindsight keeps session analyses
   for semantic recall. They answer different questions, but a smaller setup can keep claude-mem
   only and lose nothing the owner asked for.
3. **The demo surface is wide.** The Deno/Hono playground and the historical OpenCode campaign
   (`openshell-go-v5`) demonstrate things that are already published; they add services and reading
   time without adding evidence about the three pillars.

**The minimal set that still meets the four requirements:** relay + supervisor, Flue/Pi, OpenShell
(where qualified), the OTel collector + Langfuse, claude-mem, and the cockpit. That is one Compose
project, one host process, one page.

## 7. Recommendations

1. **Keep the supervisor.** It is the product, not scaffolding.
2. **Drop the Pi plugin** (superseded 2026-11-01: the owner asked what it adds beyond Flue's
   observer — tokens, cache reads, cost and latency are already there, and the raw prompts it adds
   are what the telemetry policy forbids; see the decision in
   [the plugin record](langfuse-pi-plugin.md#decision--not-adopted-2026-11-01)).
3. **Fix tier 3 with option 2 only if macOS matters.** Otherwise declare tier 3 Linux-only in the
   runbook and stop promising it locally.
4. **Do not add a third telemetry producer.** Two is the ceiling; the next step is consolidation,
   not addition.
5. **Keep the fleet strip.** It is the "one place to see every agent" the owner asked for, and it
   cost one section and thirty lines.
